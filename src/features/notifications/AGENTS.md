# Notifications — AGENTS.md

**Merges only together with the database reset.** Rules, inbox rows and delivery
rows are now read by `topic_code` and the scope columns, and a rule with neither
`topic_code` nor `category_code` means every event. Rows written before the
reset have those columns NULL (the old code wrote only `event`), so on a
database that was not wiped, every one-event rule would route every event. This
code is correct only on a freshly created database; do not add a fallback to
`event`.

"An event happened and someone should hear about it", as one data model for
self-hosted, High Availability and the store apps (decided 2026-09-18), rebuilt
around scoped, per-person preferences (2026-11-06).

**Owner decisions (2026-11-06), binding:** nothing is always on — every
notice can be turned off; a person with no preference rows hears **nothing**,
the bell included (`topic.level` is `none`), so the settings screens lead with
presets; administrators hear only organizations they belong to, plus an opt-in
`user.is_all_organizations_notified`; reading an item in the bell cancels its
held (quiet hours or digest) email; inbox rows are kept 90 days, events and the
ledger 30. Organization policies (`policy`), push (`device`), approved email
domains, shared-channel scoped routes and rate limits are later phases: the
tables and columns exist, nothing reads them yet.

Rules:

- **Routing scope.** Personal channels and the bell are decided by the person's `preference` rows only (rules on a personal channel are ignored and `PUT …/rules` answers **422** `personal_channel_uses_preferences`). An organization event reaches the organization's channels, and an instance channel only when `channel.is_all_organizations_notified` is on (API field `allOrganizations` on `/api/admin/v1/notification-channels`) or a rule names that organization in `rule.organization_id`; an install event (no organization) reaches instance channels whose rule names no organization. Routes are `rule` rows: no `topic_code` and no `category_code` means every event, otherwise one `topic_code` or one `category_code`, with a severity floor; `is_enabled` and a future `ends_at` mute. The client and admin APIs keep the shape `{ event, minSeverity }`, where `*` is the rule with neither column (`ruleTopicOf` and `ruleEventOf` in `events.ts` map both ways, and `replaceRulesForChannel` writes `topic_code` after making sure the catalog is synced, since the column has a foreign key to `topic`). Routing (`channelsForEvent`), the notification and delivery readers, and the retention SQL read only the topic and scope columns; the `event` column on `rule`, `notification` and `attempt` is still written because it is NOT NULL, and is read by nothing.
- **Audience** (`events.ts` `audience`): `members` — every teammate of the organization (`server.offline`); `managers` — holders of `organization:own` / `organization:manage` who are still members, for the events that mirror the owner-only audit trail; `admins` — install administrators, for instance events. No administrator bypass for organization events. Checked again at send time by `dropUndeliverableCopies`.
- **Leaving and deleting.** Settings die with their scope (foreign keys `ON DELETE CASCADE` on `preference`, `policy`, `rule`); history survives (`event`, `notification`, `attempt` carry scope ids as plain uuids and snapshot their text). Member removal runs `forgetMember` for that organization only. A team edit or team delete that ends membership is covered by the send-time check and the prune. The bell hides rows of organizations the person left (`visibleToUser`) and marks rows whose server, project or backup target is gone (`targetDeleted`).
- **Email.** Each personal copy carries `List-Unsubscribe` (one HTTPS link) and `List-Unsubscribe-Post: List-Unsubscribe=One-Click`, plus `List-Id`, `X-TurboPanel-Organization`, `-Project`, `-Event`, `-Reason` (`templates.ts` `notificationMailHeaders`; every sender adds `TemplateResult.headers`). An organization email channel sends only to an address that still belongs to a member (checked at fan-out and again at send). A recipient the receiving SMTP server refuses for good (`RCPT TO` 550/551/553) is suppressed (`suppression`, hashed) on the self-hosted mail path; a confirmed verification clears it. Provider bounce webhooks are not wired yet.
- **Read state.** Mark-all-read writes one `watermark` row; the unread count is capped at 100 (the bell shows 99+); reading rows (by id, at most 200 per call) or mark-all cancels the reader's own held copies (`read_in_app`).
- **Email addresses are delivered to only once known** (`channel.verified_at`, decided 2026-09-18): `POST /notification-channels` accepts the caller's own address for a personal channel and any member's account email for an organization channel, stamps `verified_at`, and answers **422** `address_not_a_member` for anything else. Any other address goes through `POST /notification-channels/email` (`src/client/notifications/verify-routes.ts`): the channel is created unverified and a one-day link is emailed to the address (`channel-verification` email job); `GET /notification-channels/verify/:token` needs no session (the address's owner may have no account), stamps `verified_at` and redirects to a fixed page. Tokens are the password-reset pattern byte for byte (`link-token.ts`: 256 bits, SHA-256 verifier with its own domain-separation context, in the existing `verification` table keyed `notification-channel:<channelId>`, no new table). A resend (`POST /notification-channels/:id/verify`) replaces the link and waits a minute (**429** + `Retry-After`). Confirming abandons every delivery written while the channel was unverified (`lastError: unverified_when_written`) so a fresh address never gets a burst of stale events. `deliverableHere` skips an unverified email channel, so a row written by another path stays `pending`.
- **The retry sweep only selects rows it can send** (`claimDueDeliveries`): channel not paused, not push, and email only when the tick has a mail queue and the address is verified. Rows for a paused channel wait untouched for it to resume and never fill the 50-row batch ahead of live channels. The batch is claimed in the same statement (`FOR UPDATE SKIP LOCKED`, retry time pushed out by the inline-attempt grace), so overlapping sweeps never send a row twice.
- **No double send.** A fresh `attempt` row carries `next_attempt_at = now + 2 min` (`INLINE_ATTEMPT_GRACE_MS`), so the 60-second retry sweep only reaches a row whose inline attempt never recorded itself; `attempts` is bumped in SQL, never read-then-written.
- **Digest and quiet hours** (`windows.ts`, `digest.ts`, `hold-settings.ts`; decided 2026-10-01, defaults): off unless a channel opts in; email, chat (Slack, Discord, Telegram) and webhook channels alike (**422** `timing_push_unsupported` for push, which the store apps own). `channel.digest_cadence` (`hourly` at the top of the local hour, `daily` at 08:00 local) and `quiet_start_minute` / `quiet_end_minute` (minutes after local midnight, may wrap midnight). At emit, a verified email channel, or a chat or webhook channel, with either setting gets a `held` ledger row (dated by the event, no retry time, so `retryDueDeliveries` never sees it) when the event is not urgent and a digest is on or quiet hours are running. **Urgent events** (`urgent` on the catalogue entry, required: outages and security changes) are never held or digested; the bell is never held. The `notification-digests` Workers phase and the Deno cleanup phase run `sendDueDigests`: per channel `releaseCutoff` (nothing inside quiet hours; with a cadence, what was held before the latest window close; with neither setting, everything, which is how held events flush when a setting is removed), then `claimHeldDeliveries` (atomic `held` to `pending` with `FOR UPDATE SKIP LOCKED`, so two sweeps never both get a row), then ONE summary per transport (grouped by event, at most 8 kinds and 5 lines per kind, counts for the rest, link back to the app): the `notification-digest` email; for Slack, Discord and Telegram a compact text (`digestText`: a head, one line per kind with severity, count and first title, the link; cut under 1900 characters for Discord's limit); for a webhook a structured JSON body (`digestWebhookBody`: `type: "digest"`, `summary`, `total`, `groups[]` with items, `moreGroups`, `consoleUrl`, `text`), signed like any event and sent with `x-turbopanel-event: digest`. Chat and webhook channels need no mail queue but the sweep must be given the data-encryption secrets (an unreadable address counts as a failed send), and the address is re-checked against the outbound URL rules like a normal send. Then the rows are `sent`; a failed enqueue puts them back to `held` (5 failures abandon). A paused channel's held rows wait untouched. The zone is the owner's `user.time_zone` for a personal channel, the organization's `defaultServerTimezone` for an organization channel, else UTC (an instance channel is UTC); a bad stored zone reads as UTC. Tests: `windows.hostfree.test.ts`, `digest.hostfree.test.ts` (pure), `digest.test.ts` (Postgres: window boundaries, urgent bypass, zones, spring-forward and fall-back nights, concurrent sweeps send once, pause/resume).
- **`server.offline` has two raisers, never both for one outage.** The stale-presence sweep announces the servers it demotes (`sweep_stale`). An ordinary disconnect (stopped daemon, dropped socket) is announced by `noticeDisconnectedServers` (`src/daemon/cell/disconnect-notice.ts`) once the server has stayed away for the sweep's grace (Workers cron: 90 s, Deno liveness timer: 150 s): one `UPDATE … RETURNING` claims every due row (`offline_reason = 'disconnect'`, not claimed, offline for at most 30 minutes) and sets `projection.offlineNoticeAt`; the reconnect clears it. It rides the existing tick (one statement served by `idx_server_offline`, no alarm, no timer, no Durable Object wake). A claim is at-most-once: a delivery cut by the tick budget is not retried. Three or more claimed in one pass follow the sweep's mass rule (the aggregate first, then the lines; the design does not dedupe them). There is no "back online" notice: the catalogue has none.
- **Planned, not built (named so the rows stay honest):** a console screen for instance channels (API only today), push.
- **Addresses are re-validated at send** through `outbound-url.ts`; every runtime passes `allowPrivateTargets: true` (a LAN Alertmanager is legitimate, decided 2026-09-18, "allow everywhere"); `false` is a test seam only. Telegram is exempt — its host is `api.telegram.org`.
- **The operator's webhook is an instance channel** (`OPERATOR_WEBHOOK_LABEL`, kind `webhook`, rule `*` at info, created with `allOrganizations` on so it still pages when a server goes dark; its switch is forced on: `adoptLegacyAlertWebhook`, which runs before every sweep alert and on the admin channel list, switches an older operator webhook on (guarded, logged, no other channel), and `PATCH` with `allOrganizations: false` on it answers **400** `operator_webhook_hears_all_organizations`; migration `0035` switched on every control plane channel that existed at that release). The legacy `ALERT_WEBHOOK_URL` setting is adopted into it on first touch (`adoptLegacyAlertWebhook` — from the admin routes and from `resolveAlertSender` per tick) and the row deleted; `PUT /api/admin/v1/settings/alert-webhook` is a thin face over that channel so the documented curl keeps working. Instance channels are managed at `/api/admin/v1/notification-channels` (`src/admin/notification-routes.ts`); an instance email channel may name any administrator's account email.
- Workers-bundle safe: no `@std/*`, no `fetch` / `crypto` at module load.
